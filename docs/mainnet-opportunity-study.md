# 用固定批次检查大额账户信号是否值得继续研究

网页关闭后就不再采样，反复刷新也会改变观察的账户范围。现在可以在本机运行独立的 Node 进程：先固定本批入组时间和对照时点，再记录候选的 1／5／15 分钟报价。运行结束后得到原始证据、检查点和对照报告。

这里验证的是价格变化和采集质量，没有下单、签名、密钥读取、手续费收取或 AI 盈利评分。它也不是交易回测：只观察第一档报价，不假设指定金额一定能成交。

## 启动一批观察

在仓库根目录执行，使用项目要求的 Node 24 或更高版本：

```bash
npm run collect:opportunities -- --minutes 60
```

`60` 表示候选入组持续 60 分钟，不是整个进程只运行 60 分钟。入组结束后继续观察，直到开始后约 75 分 20 秒自动停止。默认目录为 `output-tdd/opportunity-study/<启动时间>/`，命令启动时会打印实际路径。允许的入组时长为 1–1440 整数分钟。

例如只做一次较短的完整链路检查：

```bash
npm run collect:opportunities -- --minutes 2
```

这批约运行 17 分 20 秒。网络不佳、没有合格候选或报价缺失时，报告会保留空结果或缺测，不补示例。

也可以指定一个尚不存在的目录：

```bash
npm run collect:opportunities -- --minutes 60 --out output-tdd/opportunity-study/batch-001
```

已有目录一律报错退出，不覆盖旧记录。新一批换一个目录，或省略 `--out` 使用启动时间命名。

## 连续安排三个不同时段

想检查结果是否只出现在某一段行情，使用固定的三批计划。在仓库根目录执行：

```bash
npm run campaign:opportunities
```

命令立即启动第一批，再在启动后 2 小时、4 小时各启动一批；每批入组 30 分钟，随后观察 15 分 20 秒。比如 10:00 启动，三批约在 10:45、12:45、14:45 结束。默认目录为 `output-tdd/opportunity-campaign/<启动时间>/`。也可用 `--out` 指定尚不存在的目录，已有目录拒绝覆盖，不续跑旧计划。

采集进程先把三个时点、统一入组时长和规则版本写入 `plan.json`，再调用单批采集器。各批使用独立目录 `batch-001`、`batch-002`、`batch-003`，保留完整协议、检查点和证据。账户在每批重新发现；同一账户可以跨批出现，报告会列出重复的账户币种组合数。

电脑需要保持运行并联网。实际启动比预定时点晚超过 60 秒时，该批记为 `missed`（错过），不会醒来后集中补跑。单批失败会记录 `failed` 并等待下一个原定时点；按 Ctrl+C 或发送 SIGTERM 会保存当前中断状态，并取消未来批次。`progress.json` 保存进程号和最后状态，文件本身不能证明进程仍存活。关闭终端可能终止前台命令；这里没有安装系统服务、自动恢复或阻止休眠。

每批结束后自动更新 `summary.md` 和 `summary.json`。采集期间想读取最新检查点并重算报告，可执行下面的命令；将路径替换为启动时打印的计划目录。这一步只读取本机记录、更新这两个汇总文件，不联网、不修改原始批次数据。

```bash
npm run campaign:opportunities -- --report output-tdd/opportunity-campaign/替换为启动目录
```

汇总只读取计划内三批，不扫描其他目录。读取时会检查规则版本、预设时点、入组时长、实际启动时间、报价和采样窗口，并从原始报价重新计算价差，不信任检查点里保存的统计值。损坏或不匹配的批次显示为 `invalid`（无法核验）；失败、中断、未完成和错过的批次不进入均值，但仍列在报告中。旧试采缺少规则版本，或使用不同入组时长，不能直接混入新计划。

比较方式是先按每批的同币种、同方向、同期限计算信号和对照均值，再对两者都有有效结果的批次等权平均。比如第一批信号比对照高 2 个百分点、第二批低 1 个百分点，两批平均差值就是 +0.5 个百分点，不因第一批信号较多就给它更大权重。没有信号或有效对照的批次计为未配对；缺测保留且不当成 0。

Markdown 主表展示双边合计额外成本 10 bps；JSON 保留 0／10／20 bps 全部情景、逐批数据、差值范围及优于对照的批次数。报告中的有效/缺测数量覆盖全部完成批次，均值只取配对批次，两者的统计范围会不同。同账户、同一时段的行情仍可能相关，三批只是初步检查，不足以证明稳定优势。

## 一条记录怎样产生

假设本批从 10:00 开始。进程订阅主网 BTC、ETH、SOL 的公共成交和快速盘口，用与网页相同的规则发现成交额达到门槛的账户，固定跟踪本批最早发现的最多 6 个地址。它按仓位快照时间读取普通成交与 TWAP 分片，逐笔核对仓位链；后续只读取增量。每轮结束后至少等 30 秒再查询，遇到 429 按服务器要求和退避时间冷却。

10:02 首次核验到某账户的 BTC 多头符合候选规则时，固定当时卖一价为起点，保留原始成交和入选依据。之后同一账户、同一币种不再重复入组，即使平仓后重开或 20 分钟窗口发生变化。这样可以减少同一持仓被反复算成多个独立样本。每批候选最多 100 条；在当前 6 个账户、3 个币种的范围内，实际最多 18 个账户币种组合。

记录分别在 10:03、10:07、10:17 后的 10 秒窗口中采样，多头使用买一退出参考价，空头使用卖一。盘口的源时间和接收时间都不能早于目标时间。入组后，即使该账户减仓或不再符合规则，后续报价观察也继续。候选起点没有报价时直接留下缺测，不等待后来更有利的价格。

到了 11:00，不再发现账户或加入新候选，也不再轮询账户成交；公开盘口仍继续接收，直到最后一批后续采样窗口结束。即使一条候选都没有，预设的对照记录仍会完成或留下缺测。

## 对照组和成本怎样计算

批次启动时就把全部对照时点写入 `protocol.json`：启动后 5 秒为第一个时点，以后每隔 5 分钟一次，直到入组截止。每次为 BTC、ETH、SOL 各记录多、空两个方向，这些记录没有大户地址或入选信号，也不会冒充真实账户行为。

每个对照时点最多等待 10 秒，使用首次检查到的有效盘口固定起点，再从实际取得起点的时刻计算 1／5／15 分钟。过期的起点永久缺测，不用旧报价或后来报价回填。多空两个对照来自同一行情，不能视为互相独立的样本。

报告只在相同币种、方向和持有时长内比较。例如 BTC 多头候选的 5 分钟价差，只与本批预设时点的 BTC 多头 5 分钟价差比较，不与 ETH 或空头混合。每一组都显示有效、缺测和待采样数量；缺测不记作 0，不从总数删除。没有有效对照时不计算差值。

成本列固定展示双边合计 0、10、20 bps 三个情景。1 bps 是起点名义金额的 0.01%；10 bps 对应扣减 0.1 个百分点。例如原始方向价差为 +0.08%，10 bps 情景下为 −0.02%。这只是统一的额外成本假设，不是 Hyperliquid 的实际费率，也没有确定平台将来收取多少手续费。原始报价比较已包含买卖价差，不应再重复扣除这部分价差。

比较双方应用同一成本，所以“信号均值减对照均值”的差值不会因这个固定成本改变；成本情景主要用于检查绝对价差是否被费用消耗。JSON 中同时保留各成本情景下的正向样本数，不把它包装成交易胜率。

固定时点对照不是随机试验。批次内行情趋势、账户筛选和缺测分布都可能影响结果。不同期限的有效样本也可能不同，不能将报告各列拼成同一交易组合的连续收益。需要多批数据和进一步的统计设计，才能讨论是否存在稳定优势。

## 查看证据和停止进程

每个目录包含：

- `protocol.json`：启动前固定的时间范围、规则、成本情景和对照时点。
- `checkpoint.json`：完整候选、对照、入场盘口、后续采样、分组统计、连接与限流诊断。结果变化时保存，无变化时至少每 30 秒更新一次。
- `report.md`：同一检查点对应的中文对照报告。表中“差值”的单位是百分点。
- `evidence/`：每条首次入选候选的持仓摘要、原始仓位快照和完整 20 分钟成交窗口。`observation` 可以重新送入候选计算函数，复核窗口内退出次数等规则；文件名是候选标识的哈希，可用正文中的 `signal.id` 与检查点对应。

检查点先写临时文件，再原子替换，避免读到半份 JSON。保存失败时停止采集，不继续积累没有落盘的结果。多个文件之间不构成数据库事务；进程突然退出时，以最后一份完整 `checkpoint.json` 为准，报告可能稍旧。

终端按 Ctrl+C 会关闭订阅、取消请求，并保存“批次未完成”状态。尚未到期的点保持待采样，不冒充有效结果。第一版不续跑旧批次，重新启动会建立新批次；强制杀进程或机器休眠仍可能留下未完成记录，不能把旧文件中的“入组中”当作进程仍在运行。

这是本地进程，没有安装后台服务、云资源或定时任务。关闭网页不影响它，但关闭终端、退出进程或机器休眠会影响采集。报告覆盖的只是本批最多 6 个账户，不是全网机会。尽量不要同时运行多批或多个网页采集器，它们可能共享同一出口 IP 的接口限额。

## 检查实现

在仓库根目录执行：

```bash
node --test src/features/opportunities/lib/study.test.ts src/features/opportunities/lib/collector.test.ts src/features/opportunities/lib/study-archive.test.ts src/features/opportunities/lib/study-comparison.test.ts src/features/opportunities/lib/campaign.test.ts
npm run typecheck
npm run lint
```

`study.ts` 固定批次和对照，并复用 `followups.ts` 的到点采样与统计。`collector.ts` 负责主网只读连接、账户轮询和文件保存；`scripts/collect-opportunities.ts` 只处理命令参数和进程停止。网页的候选规则、主网交易限制和性能面板保持原有入口。

`campaign.ts` 固定三批时间表、依次启动单批采集并保存汇总；`study-archive.ts` 核验已保存批次，`study-comparison.ts` 计算批次等权结果。`scripts/campaign-opportunities.ts` 提供启动和本地重算入口。新逻辑只用于独立采集进程，没有新增网页状态或交易入口。
